## 一、财富收益曲线与顶部卡片对不上（根因定位 + 修复）

根因不是"算错"，而是**两条价格链路不同**：卡片用实时行情，曲线用"各标的最近一条历史行情"；日期轴取各标的日期**并集**并对缺失日**前向填充**，末点是混合口径（实测 09-22 只有黄金有当日点，4 只基金 T+1 + 3 只美股仍在 09-21）。

已修：
1. **曲线日期轴只保留已收盘交易日**（`profitCurve.ts`，cutoff = 昨天，用本地 `localYMD`，**不能用 `toISOString`**——那是 UTC，东八区凌晨会差一天）。
2. **基金历史被东财单页截断 20 条**：`lsjz` 的 `pageSize` 传 50/200 均无效仍返回 20（`TotalCount` 是对的），`fetchHistoryRange` 只请求 `pageIndex=1` → 区间**最早**的几天被丢。「近一月」21 个净值日必丢首日。改为 `fetchFundNav` 循环翻页（4 路并发，`TotalCount` 缺失时退回只取首页）。实测 08-24~09-22：`n=20 首=08-25` → `n=21 首=08-24`。
3. **港股历史此前恒为空**（Yahoo 对 5 位港股代码如 07266/07709 恒 404）→ 改走**东财 K 线** `push2his.eastmoney.com/api/qt/stock/kline/get?secid=116.0xxxx&klt=101&fqt=1&beg&end&fields2=f51,f52,f53`（`parts[2]` = 收盘）；A股同接口，secid 前缀 1./0.。实测 07709/07266 各 22 条（08-24~09-22），**实时价 = 历史末点，比值 1.000**；secid 映射经持仓成本核对无误（07266 成本 44.46 vs 末价 42.66；07709 成本 42.00 vs 末价 42.5）。长区间 400 天取到 230 条，**未传 `lmt` 也没被截断**（实测结论）。
4. **缓存失效**（否则"改了像没生效"）：后端 KV `HISTORY_CACHE_VERSION='v2'`，前端段缓存 `SEG_CACHE_VERSION=2`。**改上游取数逻辑必须同时递增这两处。**

## 三、全量排查发现的 3 个**今日引入的回归**（已修）

1. **`WealthImport`：批量写入失败仍扣账户余额**（旧实现是逐条 `await` 成功后才累加 `deductions`，改动后 `deductions` 在写入前就构建好了，扣款循环无条件执行）→ 钱凭空消失且重试会再扣一次。修法：加 `if (ok > 0)` 门控扣款。
2. **`AppContext`：`pulled === 0` 就跳过重读本地库** → 漏掉「远程纯删除」（删除的行不算"拉回的行"，但本地孤儿已被 `cleanOrphans` 清掉，UI 残留已删记录）。修法：`sync-engine` 让 `deleteOrphans`/`cleanOrphans` 返回删除条数 → `PullAllResult.pulled/deleted` → `syncOnStartup` 返回 `{pulled, deleted}` → 门控改 `pulled === 0 && deleted === 0`。
3. **`Budget`：`budgets.filter()` 每次渲染产生新引用** → `useMemo` 依赖 `Object.is` 永不相等 → 缓存永久失效（注释声称的优化没生效）。修法：`useMemo(() => budgets.filter(...), [budgets])`。

## 四、预存缺陷（非今日引入，**未改**，等用户决定）

- `AppContext.getBudgetProgress` 用 `now.toISOString().slice(0, 7)`（**UTC 月份**）而 `totalSpentThisMonth` 用本地月份；每月 1 号 00:00–08:00（东八区）会"用本地当月支出比对 UTC 上月预算"，总预算匹配错月。`Budget.tsx` 反而用的是正确本地 `YYYY-MM`，两处口径不一致。
- `Calendar.tsx` 分组只按「M月D日」匹配、**忽略年份**，跨年同月交易会被并进当月。
- `useHabitBadge` 的 `anyHabitEnabled` 由 `results.length > 0` 得出，而 `results` 恒为 `HABITS` 长度 → **永远为 true**。

## 八、线上端到端验证发现：港股修复在 Cloudflare Workers 里失效

推送后我到**线上接口**复验原始 bug，发现 `/api/quote/history?symbol=07709&market=HK` 仍返回 **0 条**，而**同一份代码在本机跑是 22 条**。同时 A股区间 0 条、黄金 0 条，但基金 21 条 ✓、美股 20 条 ✓。

**差异化定位**（关键手法）：拿**同一标的不同代码路径**对比 —— A股 `period` 路径走新浪 → **30 条 ✓**；A股区间路径走东财 K 线 → **0 条**。结论：**`push2his.eastmoney.com`（东财 K 线）从 Cloudflare Workers 取不到数据**（返回空 `data`），Yahoo `GC=F` 同样取不到；而 `api.fund.eastmoney.com` 与 Yahoo 美股接口在两边都正常。

**这也解释了黄金**：线上"黄金 21 条"以前看着是好的，其实那是 **KV 缓存里的旧值**；我把 `HISTORY_CACHE_VERSION` 递增后强制回源，缓存就再也掩盖不了上游失败 —— 所以我的改动是**暴露**而不是造成"黄金历史在生产环境一直取不到"。

**修法：多源兜底 + 竞速**（`raceNonEmpty`：并发发起，谁先返回非空用谁；全部失败才返回 `[]`，但**必须 `console.error` 打日志** —— 原来这条链路 `catch → []` 完全静默，是这次排查最耗时的点）。

- 港股/A股：东财 K 线 + **腾讯日K**（`web.ifzq.gtimg.cn/appstock/app/fqkline/get`，`qfq` 前复权）。**实测两源逐日完全一致**：07709 各 22 条偏差 0.00%，600519 末值 1253.800 = 东财 1253.8 ✓ 可互换。
- 黄金：Yahoo GC=F + **新浪外盘 GC 日K**（`GlobalFuturesService.getGlobalFuturesDailyKLine?symbol=GC`，JSONP）。同一标的，日收盘偏差 ≤2%；黄金只取形状（末点等比缩放到 AU9999 现价），可接受。
- 缓存版本递增到 **v3**（KV `HISTORY_CACHE_VERSION` + 前端 `SEG_CACHE_VERSION`）。

**本地验证 22/22 通过**，而且测试时**东财正好在限流我的 IP**（连续探测后直接断连）→ 这次验证恰好走的就是"主源失败 → 兜底源顶上"的路径，真实覆盖了生产场景。

**教训：涉及外部数据源时，"本地跑通"不等于"线上可用"** —— 必须打到线上接口复验；另外**静默 `catch → []` 会让这类问题完全不可观测**，至少要 `console.error`。

### 补充更正（同上）
- 措辞修正：东财 K 线在 Workers 侧不是"完全不可达"而是**不稳定** —— 在旧部署（仅东财单源）下，`07709` 曾返回 22 条、同时 `07266` 返回 0 条，说明它是**间歇性**成功；Yahoo `GC=F` 才是稳定取不到。结论不变：**必须双源兜底**，因为单源会间歇性为空、而空结果又不会被缓存（`data.length > 0` 才写缓存）→ 用户每次刷新曲线里港股都可能时有时无。
- **修复已上线并复验通过**（提交 `32946ec`，`origin/main` 已同步）：线上 `/api/quote/history` 实测 HK 07709 = 22 条（末价 42.5）、HK 07266 = 22 条（42.66）、CN 600519 = 22 条、**GOLD 从 0 条变为 21 条**、US 20 条、FUND 21 条（首日均 08-24）✓。
- **踩到的坑**：用 PowerShell 传 `git commit -m` 时，消息里带转义的 `\"` 会被解析成 pathspec 导致提交失败（`error: pathspec ... did not match any file(s)`），而随后的 `git push` 会显示 `Everything up-to-date`、很容易误判成"推送成功"。**提交信息里不要出现引号**，或改用 `-F <文件>`。
